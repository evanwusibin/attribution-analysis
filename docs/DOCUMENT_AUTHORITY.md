## 2. 冲突解决规则

1. 产品范围冲突时以 A1、A2 为准；当前主范围是售前 E1–E5 与售后 S1–S5 的一体化经营归因。
2. 生命周期或版本冲突时以 G1 为准；API、页面和数据模型只能映射它，不能另建平行状态机。
3. 数据存储、来源等级或审计冲突时以 D4 为准；外部 CRM/DMS 永远是只读来源而非归因运行域。
4. HTTP/实时事件、认证、权限与错误语义冲突时以 D5 为准；不得同时维护 `/api/chat/*` 与 `/api/v1/*` 两套业务模型。
5. 页面显示、断线恢复和可见人工边界冲突时以 D6 为准，但 D6 不得修改 G1 的领域含义。
6. 代码和运行结果仅能证明 `implemented` 或 `verified`；不得反向改变未批准的产品或领域规则。

## 3. 跨文档不变量

```text
Conversation → Case → Plan(vN) → ToolExecution → Evidence → Result(vN) → Review → Export
```

- 证据和结果只能追加新版本，历史记录不得覆盖。
- `FACT`、`MOCK`、`MISSING` 必须带来源定位与版本；关键判断含 `MISSING` 或仅 `MOCK` 时必须人工复核。
- 任何外部能力通过只读适配器接入；禁止写回 CRM/DMS，禁止直接导入旧项目业务模块。
- 售前与售后复用同一归因内核；业务场景和故障诊断域均不得复制状态机。
- Docker 组件、RAG、NL2SQL、模型和 MCP 能力只有经过实际启动/健康验证后才可标记 `verified`。

## 4. 状态口径

| 状态 | 含义 |
|---|---|
| `draft` | 内容存在，尚未完成跨文档核验 |
| `review` | 准出材料完整，等待评审 |
| `approved` | 允许按指定契约实施 |
| `implemented` | 已有实现，未必已执行验证 |
| `verified` | 已记录可复现的测试、运行或验收证据 |
| `blocked` | 受数据、规则、授权或运行依赖阻塞 |

## 5. 迁移口径

旧文档中以下说法均不再作为权威实施依据：仅售后产品范围、SQLite 作为正式运行库、售前只能在最后一个切片实施、将 WebSocket 与轮询作为互相排斥的完整异步方案、空 MCP 容器等同 MCP 服务。保留它们仅用于历史追溯，后续重构时必须明确标注已迁移。
