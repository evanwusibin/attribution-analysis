## 1. 复盘记录

### 2026-08-18 · A6 评审（P0 注释 / P1 文档补全 / P2 CRM 适配器拆分 / 运行时错误修复）

**做得好的**

1. 根因定位一次到位：MySQL 存活但请求全 500 → 快速锁定"全局单例持死连接"而非误判为配置/网络问题。
2. 修复带可复现验证：`verify_reconnect.py` 通过"关闭底层连接模拟重启"验证重连；契约测试用 mock 保证 CI 可跑。
3. 拆分保持兼容：demo.py 拆分为 readonly.py + demo_adapter.py 时保留 re-export 垫片，旧导入点零改动。

**做得不够好的**

1. 全局单例长连接是隐患：认证仓储在进程生命周期内持连接，无空闲回收与失效探测——本次 500 的直接来源。教训：跨请求共享的数据库连接必须有重连策略或短连接池。
2. 第一轮修复只覆盖了断线、漏掉了并发：`_is_connection_loss` 未覆盖 `InternalError(Packet sequence)` 等协议错乱，且未意识到全局单例连接会被线程池并发访问。教训：共享连接的验证必须包含并发场景。
3. 拆分与运行时问题先后顺序：拆分进行到一半时用户报告运行时错误，工作流被打断。教训：涉及共享单例/连接的改动前，应先做运行时健康验证。
4. E2E 脚本断言过紧：首次只接受 200/201，实际 API 用 202；`plan` 路径与真实路由 `plans/{version}` 不一致，造成两次误报 404。教训：E2E 以真实 API 契约为准，断言从宽、路由从源码核对。
